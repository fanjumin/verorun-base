## 一、项目概述

VeroRunSystem（易站 AI）是一个面向中小企业、个人创业者和电商卖家的多智能体驱动的 AI 建站与商业枢纽平台。它整合了 AI 建站、智能内容生产、电商管理、供应链对接、社交传播和金融分析等能力，通过一套统一的认证与数据体系，为商户提供从建站到运营的全链路闭环服务。

### 1.1 核心定位

- **目标用户**：中小企业主、个人创业者、电商卖家、内容创作者
- **核心价值**：多智能体自动化运营 + AI 建站 + 1688 供应链对接
- **一句话概括**：集智能建站、内容生产、电商管理、供应链对接于一体的全链路 AI 平台

### 1.2 关键能力

| 能力 | 说明 |
|------|------|
| AI 建站 | 多租户站点管理，拖拽式页面编辑，5 套内置主题，静态站点生成，一键部署 |
| AI 内容工厂 | RSS 采集 + AI 加工流水线，多平台内容一键发布，智能配图与标题优化 |
| 电商系统 | 完整的商品/购物车/订单管理，支付宝 + 微信支付，多级订阅分层 |
| 1688 供应链 | 1688 OAuth 2.0 授权对接，商品采集与 AI 优化，智能铺货到多平台 |
| 智能体矩阵 | 1 个 Master Agent + 11 个专业 Sub Agent，5 种 AI 供应商，DAG 工作流编排 |
| 统一认证 | JWT SSO 子域共享，6 种 OAuth 登录，滑块验证码行为安全，TOTP 双因素 |

## 二、技术栈总览

VeroRunSystem 采用 Python Flask 作为主后端框架，SQLite 作为统一数据库，前端使用服务端渲染（Jinja2）+ 原生 ES6 JavaScript 的组合方案。整体采用微服务集群 + 子域名路由 + 共享数据库的架构模式。

### 2.1 技术选型

| 层级 | 技术选型 | 说明 |
|------|---------|------|
| 后端框架 | Python Flask + FastAPI | Flask 主端口 8083/8084，FastAPI 独立服务 8090/8000 |
| 数据库 | SQLite | 所有服务共享 data/site.db，WAL 模式，外键约束 |
| 认证 | JWT（HS256, PyJWT） | 基于 jti 的黑名单 + 用户级吊销时间戳 |
| 前端 | Jinja2 + ES6 JS + esbuild | 服务端渲染模板，原生 JavaScript，esbuild 打包 |
| CSS | 自定义 Design System | CSS 自定义属性，深色科技风格（赛博朋克 + 玻璃态） |
| 字体 | Inter / Noto Sans SC / Orbitron | Google Fonts，英中双语排版 |
| AI 引擎 | 多供应商适配层 | DashScope / OpenAI / DeepSeek / OpenRouter / Ollama |
| 缓存 | 内存 + Redis 双模 | ali_api/services/cache_service.py |
| 任务调度 | APScheduler + DAG 引擎 | 自定义 DAG 工作流引擎 + Cron 定时调度 |
| OAuth | Authlib | 抖音 / 微信 / 微博 / 头条 / 支付宝 / 火山引擎 |
| 短信 | 阿里云 SMS | 手机验证码登录 |
| 部署 | Nginx + systemd | 反向代理 + 子域名路由 + 自动重启 |
| 头像 | DiceBear | 40+ 风格库，通过 @dicebear/collection 安装 |

### 2.2 设计决策

选择 SQLite 而非传统关系型数据库，是因为在初期阶段数据量可控，且统一数据库文件降低了多个微服务之间数据共享的复杂度。所有服务读写同一 site.db，通过 JWT SSO 统一认证，避免了跨服务的数据同步问题。

## 三、系统架构

VeroRunSystem 采用微服务集群 + 子域名路由架构。Nginx 作为统一入口，根据子域名将请求转发到不同的后端服务，所有服务共享同一个 SQLite 数据库，通过 JWT SSO 实现跨子域的统一认证。

### 3.1 部署拓扑

| 域名 | 目标服务 | 端口 | 说明 |
|------|---------|------|------|
| easykai.cn | Platform | 8083 | 门户首页 / 用户控制台 |
| platform.easykai.cn | Platform | 8083 | 平台别名 |
| agent.easykai.cn | Admin | 8084 | 管理后台 |
| captcha.easykai.cn | Captcha Service | 8090 | 滑块验证码（FastAPI） |


### 3.2 架构层次

系统分为六层：

1. **用户层**：浏览器 / 移动端
2. **网关层**：Nginx 反向代理（SSL 终止 + 子域名路由）
3. **服务层**：Platform（:8083）、Admin（:8084）、Captcha Service（:8090）、Cognition Service（:8000）
4. **核心层**：auth-center（认证中心）、Agent Matrix（智能体矩阵）、Orchestrator（自动化调度）、Analytics（分析系统）、Health（健康巡检）、ali-api（1688 供应链）、laodeng-publish（智能铺货）
5. **数据层**：SQLite（site.db 统一数据库）、Redis（缓存）
6. **外部服务**：AI 供应商、OAuth 第三方、阿里云短信、1688 API

### 3.3 蓝图嵌入模式

auth-center 模块不独立运行，而是通过 auth_blueprint.py 注册器将 8 个以上的核心蓝图同时挂载到 Platform 和 Admin 两个 Flask 应用上。这种设计让认证、用户管理、CMS 等核心功能在两个应用中共享同一套路由逻辑，避免了代码重复。

需要注意的是，platform/routes/ 和 auth-center/routes/ 都是名为 routes 的 Python 包，代码通过 sys.modules.pop（'routes', None）在导入后清理缓存来解决包名冲突。

## 六、认证与安全体系

### 6.1 JWT SSO 统一认证流程

1. 用户访问 platform.easykai.cn/login
2. 返回登录页面
3. 用户提交凭证（密码 / 短信验证码 / OAuth 第三方）
4. JWT Service 验证凭证，返回 JWT Token
5. 服务端设置 sso_token cookie（Domain=.easykai.cn），对所有子域名可见
6. 用户访问 agent.easykai.cn，Admin 服务读取同一 cookie 验证 JWT
7. 验证通过，允许访问管理后台

除了 Cookie 方式，还支持 ?token= URL 参数进行认证回调，主要用于 OAuth 完成后的重定向场景。

### 6.2 安全特性

| 安全项 | 说明 |
|--------|------|
| JWT 安全 | HS256 签名，基于 jti 的黑名单机制，支持用户级令牌吊销时间戳 |
| 滑块验证码 | 独立 FastAPI 服务（:8090），Pillow 生成拼图滑块，行为安全分析（轨迹 / 速度 / 加速度） |
| CSP 头部 | Content Security Policy 严格限制脚本和样式来源，防止 XSS 攻击 |
| 密码安全 | 哈希存储密码，强度校验，敏感词过滤 |
| OAuth 集成 | Authlib 统一管理 6 种 OAuth 登录 |
| 双因素认证 | TOTP 双因素认证支持 |
| 代理白名单 | 滑块验证码捕获代理路径白名单，防止 SSRF |
| SSRF 防护 | 请求外部资源时的白名单校验 |

## 九、开发指南

### 9.1 本地开发环境搭建

```bash
# 1. 克隆项目
git clone <repo-url> VeroRunSystem
cd VeroRunSystem

# 2. 安装 Python 依赖
pip install -r requirements.txt

# 3. 安装前端依赖
npm install
# 前端资源通过 esbuild 打包

# 4. 初始化数据库
# SQLite 数据库文件自动创建在 data/site.db

# 5. 启动服务
python platform/app.py      # 门户 :8083
python admin/app.py          # 管理后台 :8084
```

### 9.2 代码规范

项目遵循以下核心开发原则（源自 .cursorrules）：

- **先方案后代码** — 重大变更先出方案再实现
- **最小改动原则** — 只修改必要的代码，不做擅自优化
- **统一登录窗口** — 全站只允许一个登录入口
- **命名规范** — username（登录名）与 display_name（显示名）严格分离

### 9.3 版本管理

版本号的唯一源文件是项目根目录的 VERSION 文件。version.py 负责自动读取该文件，所有模块通过导入 version 获取当前版本号。

### 9.4 主题开发

主题系统基于 Jinja2 ChoiceLoader 实现模板覆盖 + CSS 变量注入。开发新主题需要遵循标准化的主题目录结构：

```
themes/<theme-name>/
├── theme.json         # 主题元数据（名称 / 作者 / 版本）
├── theme.css          # CSS 变量定义
└── templates/         # （可选）模板覆盖文件
```

目前内置了 5 套主题：
- **default** — 深色科技风格（默认）
- **light** — 浅色主题
- **nature** — 自然主题
- **ocean** — 海洋主题
- **warm** — 暖色主题

主题开发规范详见 docs/theme-development-guide.md。

### 9.5 部署配置

通过 auth-center/services/deployment_config.py 中的 DeployConfig 类统一管理开发和生产环境。配置会自动注入到所有 Jinja2 模板的上下文处理器中。
